27 tests, and the one that mattered

A walk through the data-quality layer of this pipeline, from the bottom up: what the 27 dbt tests actually are, why 26 of them reported green over a table with holes in it for eleven days, and what the 27th does differently.

A test suite made entirely of shape tests will tell you the rows you have are clean. It will never tell you a row is missing. This page is about the day that distinction cost 34 rows of production data, and the test that now makes it loud.

Part 1 · What the 27 tests are

Almost all of them are one line of YAML. You attach an expectation to a column, and dbt generates the SQL that looks for rows breaking it. A test passes when it finds zero rows. Two of the 27 are hand-written SQL files instead, because the question they ask does not fit a column-level rule.

KindCountWhat one of them means
not_null15 This column is never blank. 13 on models, 2 on the raw source.
unique7 No value appears twice. This is what enforces the grain: one row per ticker per day.
accepted_values2 Sector is one of tech, industrials, financials, crypto, benchmark. Nothing else.
relationships1 Every ticker in the fact resolves to a real row in the watchlist.
assert_positive_close_price1 Custom SQL. A clean price feed never contains a close of zero or less.
assert_fct_prices_complete1 Custom SQL. The subject of this page. Every ticker-day the source holds also exists in the fact.

Part 2 · The blind spot

What 26 of them check

That the rows which are in the table are well formed. No blanks, no duplicates, no stray sector names, no orphan tickers, no negative prices.

Every one of these passes on a table of 100 rows. Every one also passes on the same table with 34 rows quietly removed. Removing a row never creates a null, a duplicate, or a bad value.

What none of them checked

That the rows which should be there are there.

This is the whole lesson. Shape and presence are different questions, and a suite made entirely of shape tests reports green on missing data forever. An empty table would have passed all 26.

The trap in the relationships test. It looks like it covers this and does not. It checks that every ticker in the fact exists in the watchlist, which is the opposite direction of travel. A fact table with nothing in it satisfies that perfectly.

Part 3 · How the rows went missing

The fact table is incremental: each nightly run should process only new rows, not rebuild everything. The old code decided what counted as new by looking at the newest date it had already stored, and taking anything from that date onward. That marker is called a high-water mark, and it only ever moves forward.

That is fine as long as nothing ever arrives dated in the past. Your watchlist breaks that assumption, because it mixes two trading calendars.

crypto row, stored equity row, stored arrived late, rejected

Crypto trades every day. Equities do not. So the newest date in the table is always a crypto date, dragged forward across weekends while the equity calendar sits behind it. On 2026-08-06 a backfill carried equity rows for 07-28 and 08-03. Both were below the mark, so both were discarded.

The reason it lasted 11 days is the cruel part: the same filter that caused the gap also blocked every attempt to repair it. The mark never moves backward, so those rows could never arrive on any later run either.

Part 4 · Why the filter is the point of no return

flowchart TD A["A row arrives from source: NVDA, 2026-07-28"] --> B{"WHERE trade_date >= mark?"} B -- "yes" --> D["MERGE on price_key (ticker + trade_date)"] B -- "no, it is older" --> C["Discarded. It never reaches the MERGE."] D --> E["Row inserted, or existing row updated"] E --> G["fct_prices complete"] C -.-> F["fct_prices stays 34 rows short, and all 26 shape tests still pass"]

The WHERE runs first. People assume the MERGE decides what happens to a row, but a row filtered out upstream is invisible to it, so there is nothing to update and nothing to insert.

Part 5 · The 27th test

An anti-join: list every ticker-day the source has, look for its match in the fact table, and return the ones that found nothing. Zero rows returned means nothing is missing. It compares against a view over current raw data, so it re-evaluates on every run rather than hardcoding an expected count that would go stale.

tests/assert_fct_prices_complete.sql · run against production before the fix, this alone failed with Got 34 results.

Part 6 · The fix

models/02_fact/fct_prices.sql · reach back a window from the mark instead of starting at it.

Re-reading days already stored costs nothing, because the MERGE upserts on price_key: a day already present simply matches and gets rewritten with the same values. No duplicates. That is why widening the window was safe, and it is why crediting the merge strategy as the fix gets the story backwards. The merge was already there. It is the precondition that made the real fix possible.

Part 7 · The honest limit

The window bounds the exposure, it does not remove it. A backfill older than 30 days is still dropped.

That residual risk is exactly why the test stays rather than being retired by the fix. If it happens again, the build goes red instead of sitting quietly short. The window contains the failure; the test is what detects it.

Questions this usually raises

  • How was it found, if nothing failed? Not from a failure. It came from asking what the existing tests were structurally unable to see, then writing the one that would have caught it and pointing it at production.
  • Why not just full-refresh every night? That hides the defect instead of detecting it, and it stops being affordable as history grows. The test keeps working at any volume.
  • Why 30 days? It is a variable (fct_prices_lookback_days), not a constant. 30 days is about 570 rows here, so the scan is not worth optimising, and a project with a longer backfill tail can raise it without touching the model.
